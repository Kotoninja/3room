# Решения и допущения

Источник требований — [SPEC.md](SPEC.md). Здесь записаны решения о переходе и трактовка неоднозначных формулировок.

- **2026-11-26 — Переход к новой спецификации.** RoomForge используется в документации как рабочее имя из SPEC. Идентификатор npm-пакета `3room` сохраняется до отдельной задачи на переименование. Локальный конструктор одного этажа, смета, IndexedDB и экспорт входят в текущий объём. Сервер публикаций, арендаторы, облако и ML относятся к прежнему плану.
- **Переиспользование кода.** Текущие инструменты SVG/R3F, история и калибровка — основа для перехода. Существующий граф с ID вершин отличается от формата стены с `a`/`b` и собственной высотой. В T02–T04 доменная модель приводится к SPEC §5–6. Производный граф строится из единого плана в T13. Вторую редактируемую модель заводить не требуется.
- **Стек мигрирует по задачам.** Прототип до T01 использовал React 19, R3F 9, Drei 10, Tailwind и Oxlint. T01 переводит каркас на React 18/R3F 8/Drei 9, TypeScript strict, ESLint/Prettier и CI на Node.js 24. Существующий CSS и ONNX сохраняются на время перехода по задачам ниже. T05 переносит стили в CSS Modules и строки в словарь. T14–T15 заменяют FloorPlanNet/ONNX чистым TypeScript и удаляют прежнюю зависимость из штатного сценария. Этот документ не разрешает отклонений от §3.
- **Зазоры в распознавании.** В двусмысленном §8.5.10 зазор 0,6–1,3 м при выполнении прочих условий даёт одну объединённую стену с дверным проёмом. Малые зазоры сливаются по шагу 9. Остальные разрывы сохраняются.
- **Форматы.** В интерфейсе ручной импорт растра поддерживает PNG, JPEG и WebP по §8.2. JSON-экспорт проекта включает имя и план с версией 1, подложка сохраняется отдельно в IndexedDB (§13).
- **Приёмка демо.** T22 остаётся условной задачей по §16. Если она сокращается, обязательный E2E с демо из §15 всё равно требует минимальной команды загрузки демо-плана из T02, которую проверяет T24.
- **Порядок работ.** Номера T01–T25 и календарь взяты из §16. Связи в трекере отражают технические предпосылки. Для общей последовательности и правил сокращения используется §16. Старые статусы resolved относятся к прежней версии продукта и не заменяют приёмку T-задач.
- **T02 — Граница доменной модели.** `src/model` определяет формат плана и проекта версии 1. Схемы проверяют конечные числа, положительные размеры, уникальность ID внутри коллекции и принадлежность проёма стене. ID остаётся непустой строкой по контракту `Id`, демонстрационные ID фиксированы для воспроизводимости. Комнаты вычисляются из стен и не сериализуются. Существующий стор редактора продолжает работать до миграции в T04. Вычисление графа и загрузка демо в интерфейсе выполняются по своим задачам.
- **T02 — Подложка до калибровки.** Значение `metersPerPixel: 0` обозначает загруженную, ещё не откалиброванную подложку, чтобы §6.3 мог сохранить её сразу. Калибровка задаёт положительный масштаб. Схемы также проверяют диапазон прозрачности, порядок меток времени и непустое имя проекта. В метрических проверках границ используется погрешность 10⁻⁹ м. Правило непересечения проёмов при размещении относится к T12.
- **T03 — Границы геометрических функций.** Допуск касания отрезков — 10⁻⁶ м, измеряется как расстояние. Для близкого Т-стыка возвращается проекция ближайшего конца на второй отрезок. Коллинеарное наложение возвращает `null`, поскольку общей точки с однозначным положением нет. Отрезок нулевой длины считается точкой. Граница простого полигона считается принадлежащей полигону с тем же допуском. Полигон нулевой площади не содержит точек, его центроид возвращает среднее вершин, а у пустого — `(0, 0)`. Нормализация нулевого вектора возвращает нулевой вектор.
